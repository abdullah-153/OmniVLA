OmniVLA: System Architecture Deep Dive

Document 01 — Complete Technical Specification

1. Architectural Philosophy

OmniVLA's architecture is built on a single principle: "No single module should require intelligence beyond what a 4B-parameter model can reliably provide."

This means:

  • Perception is handled by deterministic APIs and lightweight CV (no LLM inference)
  • Planning is done by the LLM operating on pure text (no visual tokens)
  • Action selection is constrained by formal grammars (LLM can't hallucinate invalid actions)
  • Execution is deterministic (no LLM inference for mouse movement)
  • Verification is heuristic-based (pixel diff + semantic re-parse)

Why Not End-to-End VLM?

End-to-end VLMs (like Anthropic Computer Use or GPT-4o) process raw screenshots and output actions. This requires:

  1. A vision encoder (~1-2GB VRAM) to process the screenshot
  2. A large language model (~8-30GB VRAM) to reason about it
  3. Sufficient reasoning capacity to simultaneously understand, plan, and precisely locate targets

With 6GB total VRAM, this is impossible. Even a quantized 3B VLM like Qwen2.5-VL-3B would consume ~4GB for the model + ~1.5GB for vision encoding + KV cache, leaving zero headroom.

Our approach: Run a text-only LLM at full capacity (~4.5GB) and handle all visual processing on CPU with zero VRAM cost.

3. Module Interface Specification

3.1 SemanticState — The Central Data Object

The SemanticState is the lingua franca of the entire pipeline. Every module produces or consumes it.

@dataclass
class InteractiveElement:
    id: int              # Sequential ID (1, 2, 3...)
    type: str            # button, text_field, link, label, icon, tab, menu_item
    label: str           # Human-readable label (max 60 chars)
    region: str          # Spatial location: top-left, center, bottom-right, etc.
    bbox: tuple          # (x1, y1, x2, y2) pixel coordinates
    center: tuple        # (cx, cy) click target
    confidence: float    # Detection confidence (0.0-1.0)
    source: str          # "uia" | "ocr" | "yolo" — how it was detected

@dataclass
class SemanticState:
    app: str                       # Active application name
    window_title: str              # Full window title
    layout_type: str               # browser_webapp | desktop_app | dialog | menu
    webapp_name: str               # If browser: Gmail, Sheets, etc.
    elements: list[InteractiveElement]  # Max 20 elements
    visible_text_summary: str      # 1-2 sentence summary of visible text
    is_dialog: bool                # Is a dialog/modal open?
    is_menu_open: bool             # Is a context/dropdown menu visible?
    screen_change: str             # What changed since last capture
    timestamp: float               # Capture time
    screen_width: int              # Resolution width
    screen_height: int             # Resolution height

3.2 Token Budget for Semantic State

The state must be compressed to ~150-200 tokens for the LLM prompt. Here's the breakdown:

App: Excel                                    ← 3 tokens
Window: Book1 - Excel                         ← 6 tokens
Layout: desktop_app                           ← 3 tokens
Screen: 1920x1080                             ← 5 tokens
Text summary: Spreadsheet with columns...     ← 15 tokens
Interactive elements:                         ← 2 tokens
  [1] button: "File" (top-left)               ← 8 tokens × 15 elements
  [2] tab: "Home" (top-left)                  = 120 tokens
  [3] button: "Paste" (top-left)
  ...
Last change: New window opened                ← 5 tokens
─────────────────────────────────────
TOTAL:                                        ≈ 155 tokens

This leaves ~1500 tokens for the system prompt, sub-goal, memory context, and model reasoning — well within a 2048 context window.

4. Error Handling & Recovery Architecture

4.1 Error Taxonomy

ERROR TYPES:
│
├── PERCEPTION ERRORS
│   ├── UIA tree empty (custom app / Electron)
│   │   └── Fallback: OCR + heuristic element detection
│   ├── OCR misread text
│   │   └── Fallback: Try UIA label, or re-capture with higher resolution
│   └── Window not found
│       └── Fallback: Wait 1s + retry, or ask user
│
├── REASONING ERRORS
│   ├── LLM selects wrong element ID
│   │   └── Recovery: Verify via screen diff, retry with enriched context
│   ├── LLM outputs done() prematurely
│   │   └── Recovery: Semantic verification detects incomplete state
│   └── LLM in reasoning loop
│       └── Recovery: Max 5 actions per sub-goal, then re-plan
│
├── EXECUTION ERRORS
│   ├── Element no longer visible (UI changed)
│   │   └── Recovery: Re-perceive, re-reason
│   ├── Click lands on wrong target
│   │   └── Recovery: Screen diff + undo (Ctrl+Z) + retry
│   └── Application crash / unresponsive
│       └── Recovery: Wait 3s, check process list, escalate to user
│
└── VERIFICATION ERRORS
    ├── Screen didn't change (action had no effect)
    │   └── Recovery: Try alternative execution method (shortcut → UIA → click)
    └── Unexpected screen (wrong state reached)
        └── Recovery: Re-plan from current state

5. Concurrency & Threading Model

Main Thread (Python asyncio):
│
├── Agent Orchestrator Loop
│   ├── Perception calls (sync, fast)
│   ├── LLM inference (sync, blocking — GPU-bound)
│   └── Execution (sync, brief)
│
├── Background: ChromaDB operations (async)
├── Background: Screenshot buffer (pre-capture next frame)
└── Background: Health monitoring (LLM server status)

Important: The LLM inference is the bottleneck. All other operations are <100ms and can run between inference calls. There is no benefit to parallelizing perception and reasoning because they are sequential dependencies.
